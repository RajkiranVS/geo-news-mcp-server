Who picked the new feed?

With feed routing written into the prompt, — of — models ever chose the feed I added. With routing moved into the tool's own schema, — of — did, each in its own way.

A follow-up to my geopolitical-news MCP server on AWS Lambda. Four models, four runtimes, ten questions, 26 November 2026; Round 3 added 27 November. By Rajkiran Veldur. Data and eval code: geopolitical-news-agent-vLLM.

One server, a fourth feed

The MCP server has one tool, get_feeds, which reads an allowlisted set of RSS feeds and filters them by keyword. It is called from Bedrock AgentCore (Nova Pro), Microsoft Foundry (gpt-5.6-luna), Google ADK (gemini-3.8-flash) and a local vLLM agent (Qwen2.5-3B).

I added a fourth feed, aljazeera_all, described in the schema as world news with in-depth coverage of the Middle East, Africa and the Global South. Then I asked every agent the same ten questions: four where Al Jazeera clearly fits (Gaza, Sudan, Lebanon, the Sahel), three Indian domestic ones where it does not, and three world ones where it is optional.

Prompt routing: the new feed never gets picked

Every agent's system prompt still listed the three old feeds with rules for when to use each. The new feed was in the tool schema, with a description, on every runtime.

On questions where Al Jazeera fits, it was chosen on — of — first calls. The prompt's list won over the schema every time, on every model.

Move routing into the schema

I deleted the feed list and the routing rules from each prompt and replaced them with one line. The schema already says what each feed covers.

- Available feeds: bbc_world (world news), hindu_international (...),
-   hindu_national (Indian domestic news).
-   - World or international topics: use bbc_world and hindu_international.
-   - India-specific topics: add hindu_national.
+ feed: choose every feed whose description in the tool fits the question.

Nova Pro, gpt-5.6-luna and gemini-3.8-flash then picked Al Jazeera on —, — and — of 4 questions where it fits. Qwen, the 3B model, managed — of —.

Examples do double duty

Qwen's problem was not routing. Removing feed names from the prompt's examples also removed the only demonstration that feed is a list. Qwen then sent it as plain text on — of — runs, and the server rejected those calls.

One placeholder example, feed: ["<feed>", "<feed>"], fixed the format, and Al Jazeera hits rose to — of —. But — of those calls also asked for reuters_africa, a feed that does not exist. More on that below.

Choosing is not the same as including

A model can "use" the new feed by adding it to everything. On the three Indian domestic questions, where Al Jazeera adds nothing, Nova Pro still included it — of — times, gemini-3.8-flash — and gpt-5.6-luna —.

The same line, "every feed whose description fits", read as "include them all" for Nova and as "route" for gpt-5.6-luna, which also narrowed: the RBI question went to the Hindu national feed alone. Hit rate alone flatters an include-everything model, so the false-pick rate belongs beside it.

One caution on Nova's pattern: on the hosted runtimes all ten questions ran in one chat session, so Nova could see and repeat its earlier calls. In a later rerun with a new session for every question, it no longer sent all four feeds every time.

Better routing also meant fewer wasted calls. Under prompt routing gemini-3.8-flash retried Gaza — times in all, hopping from "ceasefire" to "Hamas" to "Israel", but never tried another feed. With schema routing it needed —. Across all ten questions its tool calls fell from — to —.

What broke along the way

  • A strict filter met a reasonable keyword. gpt-5.6-luna searched "India Supreme Court" across three feeds and got — story, a US one, which came in through the Hindu international feed. gemini-3.8-flash searched "Supreme Court" and got — Indian rulings, across the same three feeds and again when it asked the Hindu national feed alone. Indian news rarely says "India", and my filter needs every word to match. The keyword, the feed choice and the filter each played a part.
  • The allowlist held, recovery did not. Qwen's invented reuters_africa failed validation, so the whole call was rejected, and the valid Al Jazeera feed in the same call was never fetched. Qwen did not retry and told the reader there were "no matching headlines".
  • Relevance drift. Asked about Gaza ceasefire talks, one answer listed strikes and a celebrity item, with no note that nothing covered the talks. Whatever passes the filter tends to get presented.
  • Format. gemini-3.8-flash dropped the markdown links in both conditions, so readers could not check its sources.
  • Retries. Each model broke "retry once with a broader keyword" its own way: dropping the keyword, swapping it, skipping the retry, or hopping between related names.

Round 3: put the example in the schema

A reader, Louis Philip, suggested a stricter design: keep the schema as the single source, put an array example there, and stop teaching the format in the prompt. So I added examples: [["hindu_national", "hindu_international"]] to the feed field, deliberately leaving out Al Jazeera so the example could not nudge the questions it fits, and removed the format example from Qwen's prompt.

The example reached the model: I confirmed it in the request LangChain sent to vLLM and in the declaration ADK sent to Gemini. Qwen then sent a valid list on all — runs, with — sent as text, and picked Al Jazeera on — of —, with no invented feeds.

This round also fixed a flaw in my own method. In rounds 1 and 2 each hosted runtime answered all ten questions in one chat session, so a model could repeat its earlier calls. Round 3 used a new session for every question. The hosted models picked Al Jazeera on — of — questions where it fits, so the main result held.

The example did steer the small model: Qwen added hindu_national, one of the example's feeds, to Ukraine and US–China questions. The large models did not.

Small models still need a few prompt examples

Louis's strict version was no prompt examples at all, so I gave Qwen gpt-5.6-luna's exact prompt, which has none, and kept the schema example. Its calls broke again: feed went out as text on — of — runs, and three more runs looped on rejected text calls until they hit the step limit. That is about the same as with no schema example at all.

So the schema example only worked alongside a few prompt examples showing the call pattern (question → keyword), even though none of them showed the feed format. Which part of those examples matters, this data cannot say. The three large models never needed either.

A check that fails when routing regresses

The last suggestion was to keep the unrelated questions as a permanent check. check_routing.py now runs every question three times against rules in questions.json: a feed that must not appear fails, a feed that should appear warns, and a text feed, a missing call or a loop fails too. What I would tell another builder

  • Put routing knowledge where the tool lives. A prompt that names the options freezes them; a schema description travels to every runtime.
  • Check what your prompt's examples also teach. Mine taught the argument format as well as the content.
  • Put format examples in the schema, but keep two or three call-pattern examples in the prompt for small models, and choose example values that cannot steer routing.
  • Run the same questions as a pass/fail check on every schema change.
  • Use a new session per question when you evaluate, or the model grades its own earlier answers.
  • Measure false picks and calls per question, not just hit rate.
  • Retrieval, relevance and faithfulness fail separately. A citation check proves a fact has a source, not that the answer fits the question.
  • Next on the server: drop unknown feeds and report them in failed_feeds rather than rejecting the whole call.

Caveat: each runtime used a different model, so this compares model and runtime pairs, not clouds. Hosted runs are one run per question, and in these rounds all ten questions shared one chat session, so a model could repeat its earlier calls. The first question, Gaza, had no earlier call to repeat, and its pick flips from no to yes on every hosted model. A rerun with a new session per question kept the result: the hosted models picked Al Jazeera on 11 of 12 questions where it fits. Qwen ran three times each at temperature 0. Feeds are live, so answers drift within hours; only the feed and keyword choices are compared across conditions.

Corrections and how this was checked

  • One session per runtime. Rounds 1 and 2 on AgentCore, Foundry and ADK ran all ten questions in one chat session. The Gaza question, asked first, had nothing to copy and flipped on every hosted model; Round 3 reran everything with fresh sessions and the result held. Nova's "all four feeds every time" pattern did not repeat with fresh sessions.
  • "The keyword, not the model". My first draft blamed the keyword filter alone for the Supreme Court miss. The model's keyword, its feed choice and my filter each played a part.
  • A hypothesis withdrawn. One Nova call that dropped Al Jazeera looked like the example steering it. It had run on an old prompt: the AgentCore playground resets the prompt on every new session.
  • Counting. Qwen's 9 of 12 with a prompt example includes three calls the server rejected for naming a feed that does not exist.

Every finding, including the withdrawn ones, is numbered in the lab notebook. Raw data: tool_calls.csv, observations.csv, regression.csv. The check: check_routing.py and questions.json.

How the numbers were made
  • A pick counts when aljazeera_all is in the first get_feeds call for a question. Retries are counted in tool calls, not in picks.
  • Qwen ran each question three times at temperature 0, so its counts are out of 12, 9 and 30 rather than 4, 3 and 10. Runs with no tool call count as no pick.
  • Qwen's three schema_format Sahel calls count as picks although validation rejected them, because reuters_africa was in the same call.
  • The Sudan and Supreme Court item counts come from the tool outputs in each runtime's trace, recorded by hand.
